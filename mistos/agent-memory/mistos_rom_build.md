**Critical gotcha found post-"success":** the first build that reported success actually shipped the WRONG kernel — a stock, non-rooted kernel from `device/google/shusky-kernels/` (populated by `repo sync`, kernel release `6.1.124...ab13202960`, built March 2025), not the custom `blu_spark-17-susfs` kernel actually built at `~/kernel/out/shusky/dist/` (release `6.1.157...ab16012876`, built Aug 2026). `device/google/shusky/device-shiba.mk` sets `TARGET_KERNEL_DIR := device/google/shusky-kernels`, and `BOARD_PREBUILT_BOOTIMAGE := $(wildcard $(TARGET_KERNEL_DIR)/boot.img)` in zuma's BoardConfig-common.mk reads straight from that repo-synced directory — nothing automatically copies the separately-built kernel's `~/kernel/out/shusky/dist/` output into it. Confirmed by extracting+decompressing boot.img's kernel payload with `unpack_bootimg` + `lz4 -d` and comparing `Linux version` strings — do NOT trust a matching boot.img file size/checksum alone as proof, always check the actual kernel version string inside.

**Correction (this was backwards at first):** the initial diagnosis above was WRONG in a way that caused real damage. `device/google/shusky-kernels/` (repo-synced) actually already held the CORRECT, newer custom kernel (`6.1.157...ab16012876`, built 2026-08-04) — it was `~/kernel/out/shusky/dist/` that held a STALE build (`6.1.124...ab13202960`, built 2025-03-12) with KernelSU-Next/SUSFS never actually compiled in. Overwriting `device/google/shusky-kernels/` with the stale `~/kernel/out/shusky/dist/` output (as described above) was a regression, not a fix — always verify which side is actually newer/correct by decompressing and reading the `Linux version` banner string (`unpack_bootimg` + `lz4 -d` + `strings | grep -i "linux version"`) on BOTH sides before overwriting either one, never assume the separately-built kernel tree is automatically the "right" one.

**The real root cause:** in `~/kernel`, a full custom defconfig `aosp/arch/arm64/configs/blu_spark_defconfig` (diffed cleanly against a preserved `stock_defconfig` — the meaningful delta is just ~236 lines: the `CONFIG_KSU`/`CONFIG_KSU_SUSFS*` block, `CONFIG_UNAME_OVERRIDE*`, `CONFIG_LTO_CLANG_FULL`, `CONFIG_TCP_CONG_BBR`, etc.) was created but **never wired into the Bazel build** — `private/devices/google/shusky/BUILD.bazel`'s `defconfig_fragments` filegroup only listed zuma's fragments + a tiny 677-byte `shusky_defconfig`, with zero reference to `blu_spark_defconfig` anywhere in the tree. So every kernel built via `./build_shusky.sh` silently used a config with no KernelSU/SUSFS at all, even though the defconfig file existed on disk. Confirmed via: `grep -rl blu_spark private/ aosp/BUILD.bazel` (no hits) and zero `nm`/build-cache hits for kernelsu/susfs objects anywhere. Note `CONFIG_KSU_SUSFS_HIDE_KSU_SUSFS_SYMBOLS=y` means a plain `strings`/`nm` search of a *correctly-built* KSU/SUSFS kernel will ALSO show nothing — that check is not reliable proof of absence by itself; check the Bazel `defconfig_fragments` wiring and build logs instead.

**Fix applied (now actually verified working, as of 2026-09-16 14:18):** copied `blu_spark_defconfig` into `private/devices/google/shusky/blu_spark_defconfig` and added it as the last entry in that package's `defconfig_fragments` filegroup in `BUILD.bazel`. Two more real issues surfaced once that fragment actually applied:
1. Toolchain-auto-detected fields baked into `blu_spark_defconfig` from whatever environment it was originally captured in (`CONFIG_CC_VERSION_TEXT`, `CLANG_VERSION`, `AS_VERSION`, `LLD_VERSION`, `PAHOLE_VERSION`) conflicted with this tree's actual toolchain and made Kleaf's config-merge validation fail outright — stripped those 5 lines from the copied fragment (left the original `aosp/arch/arm64/configs/blu_spark_defconfig` untouched).
2. `device.bazelrc` defaults to `--use_prebuilt_gki=true` with a pinned official build number (`13202960` — this is exactly the stale `.124`/March-2025 kernel's build-ID suffix), so the base GKI kernel is normally downloaded rather than built from this tree's local (newer) `common/` source, which caused a hard "KMI or sublevel mismatch" between our from-source device kernel (`.157`) and that stale downloaded base (`.124`). Fixed by building with `--config=use_source_tree_aosp` (sets `--use_prebuilt_gki=false`, `--kernel_package=@//aosp`) so both sides build from the same local source. This also surfaced (and required fixing) a latent, previously-never-exercised checked-in-defconfig drift: `aosp/arch/arm64/configs/gki_defconfig` had a stale `# CONFIG_USB_RTL8150 is not set` line that doesn't round-trip through Kleaf's `savedefconfig` validation — removed it.
3. `CONFIG_NET_PKTGEN=m` (part of blu_spark's fragment) produces `net/core/pktgen.ko`, which Bazel's `kernel_build` rule requires explicitly declaring — added it to `module_outs` in shusky's `BUILD.bazel` (`ZUMA_MODULE_OUTS + ["net/core/pktgen.ko"]`, not the shared zuma-wide list).

Verified success this time via three independent signals, not just a clean exit code: (a) the build log literally prints `-- KernelSU version: 32525` / `KSU_NEW_DCACHE_FLUSH` / a Manager signature hash during the KernelSU driver's own configure step, (b) `~/kernel/out/shusky/dist/.config` has `CONFIG_KSU=y` and the full `CONFIG_KSU_SUSFS_*` block, (c) the resulting kernel's `Linux version` banner string carries a `-dirty` suffix (`6.1.157-android14-11-g3240d8f38125-dirty`) proving it's genuinely a local build with uncommitted changes, unlike every previous candidate which had a clean official-looking `-abNNNNNNNN` CI build suffix and no KSU. A supervisor script `~/kernel_build_supervisor.sh` (same retry-on-kill-vs-real-error pattern as the ROM one, now invoking `tools/bazel run` directly with the extra `--config` rather than going through `build_shusky.sh`'s wrapper) handles the shared server's memory pressure during rebuilds.

**After a kernel rebuild, the `~/kernel/out/shusky/dist/` → `device/google/shusky-kernels/` copy step must always be redone** (boot.img, dtbo.img, Image variants, modules.*, blocklists, dtb files, full `.ko` set replace including any newly-added modules like `pktgen.ko`) to actually get the rebuilt kernel into the ROM build — there is no automation for this yet, and it's easy to think a "successful" kernel build alone is enough when it isn't.
